# 팟캐스트 자료 수집

## 입력과 발굴 자료 인계

- 확정된 주제·범위와 사용자 자료를 받는다. 제작 흐름에서는 brief.md를 먼저 읽는다. 주제가 미정이면 상세 조사를 시작하지 않고 주제 선택이 필요함을 알린다.
- 발굴을 경유한 회차는 brief.md에 고정된 **선택 스냅샷**을 기준으로 조사한다. 선택 ID·확정 질문·포함/제외 범위·선택한 사용자 표현과 시각·제작 의사·출처의 원래 제공자·미확인 사항이 있어야 한다. 탐색 경로만 있고 이 기록이 없거나 brief 내부 내용이 모호·불일치하면 중단해 누락된 선택 근거를 보고한다. 현재 discovery.md의 선택으로 과거 승인을 추정하지 않는다.
- 원 discovery.md는 추가 맥락용이다. 이후 selected_candidate·status가 바뀌거나 탐색 파일을 읽을 수 없어도 완전한 회차 스냅샷을 무효화하지 않는다. 기존 회차의 주제와 출처를 현재 선택에 맞춰 교체하지 않는다.
- 발굴 경유 시 스냅샷의 출처를, 직접 주제가 주어졌다면 사용자 자료를 읽는다. 추천/조건부 판정은 조사 우선순위이지 사실 검증 결과가 아니다. 원문 접근·최신성·수치·적용 조건을 다시 확인하고, 조건부 주장은 해소하거나 한계와 함께 기록한다. 요약이나 검색 스니펫만 사실 근거로 삼지 않는다.
- 출처의 원래 제공자를 유지한다. 사용자가 직접 준 링크·문서만 sources.json의 kind를 user로, 발굴 단계가 찾은 링크는 search로 기록한다. 사용자가 후보를 선택했다고 검색 출처가 사용자 제공 자료로 바뀌지 않는다.
- 같은 원전을 인용한 여러 글은 독립 근거로 세지 않는다. 블로그가 직접 구축·운영한 경험은 해당 사례의 1차 출처로 다루되, 회사 내부 수치와 일반적인 사실을 구별한다.

## 우선순위

1. **사용자가 준 자료가 기준이다.** 주제의 범위와 관점은 여기서 정해진다. 전부 읽는다
2. **검색은 빈틈만 채운다.** 사용자 자료가 다루지 않는 정의, 배경, 최신 상태(버전, 지원 종료 여부 등)만 찾는다. 사용자 자료와 충돌하는 최신 정보가 나오면 둘 다 기록하고 충돌을 표시한다
3. **1차 출처를 우선한다.** 공식 문서, 릴리스 노트, 프로젝트 저장소, 원 논문. 요약 블로그는 1차 출처를 찾는 길잡이로만 쓴다

사용자 자료가 없으면 발굴 단계에서 받은 검색 출처도 활용하되, 출처를 최소 3개 이상 서로 다른 곳에서 확보한다. 인용 관계를 확인해 세 링크를 독립 검증 세 건으로 오인하지 않는다.

## 산출물

`sources.json` — 출처 하나당 한 항목.

```json
[{"id": "src1", "title": "…", "url": "https://…", "kind": "user"},
 {"id": "src2", "title": "…", "path": "docs/…", "kind": "user"},
 {"id": "src3", "title": "…", "url": "https://…", "kind": "search"}]
```

`research.md` — 대본 작가가 이것만 보고 쓸 수 있게.

- 맨 위에 주제 범위 한 단락: 이번 회차가 다루는 것과 다루지 않는 것
- 사실은 한 줄에 하나, 끝에 근거 출처 id: `- etcd 스냅샷은 … 한다 [src1, src3]`
- 출처마다 다른 주장은 `충돌:` 줄로 남긴다
- 청취자가 낯설어할 약어와 원래 이름 목록 (대본의 약어 풀이에 쓰인다)
- 출처 문장을 길게 옮기지 않는다. 자기 말로 요약하고, 꼭 필요한 인용만 짧게 둔다. 대본으로 넘어가는 문장이 원문을 베끼지 않게 하려는 것이다

## 게이트

`python3 -m tools.check_links episodes/<id>` 로 모든 출처가 살아 있는지 확인한다. 실패하면 오케스트레이터의 재시도 규칙을 따른다.
